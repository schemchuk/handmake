# Review: product vision v2 (spec v5, architecture v3, ADR 010-014)

Reviewer: kimi-code · Author: claude-code · Date: 2026-10-28
Brief: docs/reviews/2026-10-28-v5-brief.md. Scope: review only, no code changes.

**Verdict: approve with changes** — the direction fits the code base well, but three gaps (B1-B3)
must be closed in architecture v3 / tasks v3 before the phase-1b contest work can be implemented as
described.

## Blocking findings

### B1 — The Worker cannot learn channel message ids (poll close, withdrawal edit)

Where: architecture 4.4 steps 3-4 ("the ledger stores the poll message ID; it is found by op kind"),
ADR 010 withdrawal via `editCaption`.

The poll and album message ids exist only in `content/ledger/<postId>.json` as a bare `remoteIds`
prefix — op kinds are not recorded (`packages/core/src/ledger.ts`). The D1 index
(`apps/bot/migrations/0005_published_posts.sql`, `indexPublished` in `apps/bot/src/draft-store.ts`)
stores only `(tenant_id, post_id, published_at, photos)`. The callback body
(`packages/core/src/published-callback.ts`) carries `{tenantId, postId, date, photos, channels:
{…: "done"|"failed"}}` — no remote ids. So the closing cron (arch 4.4 step 4) and the withdrawal flow
(ADR 010) cannot know which Telegram message to stop or edit without fetching post + ledger from Git
and re-rendering ops to find the poll index — heavy for a Worker cron and fragile (the render must be
byte-identical weeks after publishing, or the index is wrong).

Proposed fix: extend the published callback (T18/T19 schema) with per-channel landmarks the publisher
already knows at deliver time — e.g. `channels: { telegram: { status, albumMessageId, pollMessageId?
} }`, computed as `remoteIds[ops.findIndex(o => o.kind === 'poll')]` — and store them in D1 (new
columns on `published_posts` or a `channel_deliveries` table). This also resolves the PR #31 N1 note
("find the poll by op kind, not by index") at the source instead of re-deriving it downstream.
Prerequisite for the close cron and withdrawal tasks (T29/T30/T31 in the split below).

### B2 — Display names must not ride the `repository_dispatch` payload

Where: architecture 4.4 step 3 / ADR 010: "the dispatch payload carries the entries' file_ids and
display names".

ADR 010's own core principle is that names live in exactly one deletable place (D1). A
`client_payload` is retained by GitHub with the workflow run/event; the repo and its Actions logs are
public; and there is no clean erasure path for a name inside a past dispatch event — a withdrawal
would delete D1 but leave the name in GitHub's records. That breaks the ADR's guarantee and the
F14/Q13 intent ("names stay out of Git", "one deletable place").

Proposed fix: the payload carries entry ids only (inside the `{entry:<id>}` placeholders, as
designed). The publisher resolves names through the same HMAC endpoint the site build uses
(`GET /internal/contest-names`, ADR 011), reusing the PUBLISH_CALLBACK_SECRET pattern. Resolution is
per channel: names for Telegram, always "Work No N" for Instagram (capability-driven, not a network
branch). One mechanism, no personal data in GitHub event payloads at all.

### B3 — Draft kind is neither persisted nor dispatched; works have no publisher path

Where: architecture 4.4/4.6 assume typed drafts (`wotw-poll`, `work`) reach the publisher.

- The `drafts` table (migrations 0001-0005) and `Draft` in core have no kind column.
- `publishJobOf` (`apps/bot/src/bot.ts:553`) builds `{tenantId, postId, texts, fileIds, provenance}`
  and `createGitHubActionsRunner` (`apps/bot/src/publish-runner.ts`) sends exactly those fields — no
  `type`, no `poll`. The publisher schema already accepts them
  (`apps/publisher/src/payload.ts`), and `publish.yml` passes everything through except `.live`
  (`jq 'del(.live)'`), so the missing piece is bot-side. Side effect observed today: T20 announcement
  and reminder posts are committed as `type: free` (the payload default) — the committed history no
  longer distinguishes recurring posts.
- For `work` there is no path at all: `buildPostFromPayload`
  (`apps/publisher/src/build-post.ts`) only builds posts and `GitRepoContentStore` only writes
  `content/posts/`; works need different frontmatter (`collection`, `sale?`, `video?`) and folder.

Proposed fix: a `drafts` migration adding `kind` plus a kind-extras JSON (poll spec, collection,
entry refs); extend `PublishJob` and the dispatch client_payload with `type`/`poll` and a `kind:
'post' | 'work'` discriminator; add `buildWorkFromPayload` + a works writer in the content store
(the ledger path `content/ledger/<id>.json` is id-keyed and reusable as-is). Fix forward on the
announcement type (send `type` from now on); no backfill needed.

## Non-blocking findings

- **N1 — `editCaption` is the wrong capability shape.** With layout O1 the UA text over 1024 chars
  becomes a separate text message and the DE version is a text reply; a name in either needs
  `editMessageText`, not `editMessageCaption`. Make the capability `editMessage` (caption or text,
  adapter decides). Withdrawal also needs the target message id — covered by B1.
- **N2 — ADR 010 is internally ambiguous: "new draft type `entry`" vs. storage in a separate
  `contest_entries` table.** Recommend the table (see answer 3). Note the `drafts` table's
  one-collecting-draft-per-chat index and `latestForChat` already collide between cron drafts and a
  collecting post (review-notes, T20); adding `/entry` and `/work` sessions into the same per-chat
  "latest draft" channel would make that worse — the flows need an explicit per-chat session kind.
- **N3 — 90-day entry deletion anonymizes the site's winners page retroactively.** The site resolves
  names at build time; after deletion every old winner renders "Work No N". F22 wants a winners
  showcase — confirm with Volodymyr that this privacy-over-showcase outcome is intended (or extend
  consent at collection time).
- **N4 — Site job wiring details.** (a) `publish.yml`'s `workflow_dispatch` currently *requires* a
  payload input; a manual site rebuild via the same file conflicts — make the payload optional and
  the publish job conditional, or give the site its own workflow file. (b) A `site` job with
  `needs: publish` checks out the event SHA by default, which predates the content commit the publish
  job just pushed — the site job must `actions/checkout` with `ref: main` explicitly. (c) Give
  `site`/`render-video` their own concurrency groups so a slow Pages deploy or render never queues
  behind `publish` (or blocks it).
- **N5 — Personal data in public Actions logs.** Actions logs of a public repo are world-readable.
  The site job and the publisher (after B2) must never echo the contest-names response or Impressum
  values; mask fetched values with `::add-mask::` on receipt. Scope `CLOUDFLARE_API_TOKEN` to Pages
  only (ADR 011 already implies this; make it explicit).
- **N6 — The contest-names endpoint is a GET; the callback's HMAC-over-body scheme does not apply.**
  Define the auth explicitly: signature over `method + path + timestamp` with a short freshness
  window against replays, same constant-time compare (`secretsEqual` exists in
  `apps/bot/src/composition.ts`).
- **N7 — Doc nits.** Architecture section 4.5 (failure handling) sits after 4.9; renumber. ADR 014:
  "the content schema rejects `sale` on contest entries" — entries never enter the content store
  (ADR 010); only `wotw-result` posts and the works schema need the rule.
- **N8 — ADR 012 licence caveat can be resolved positively.** HyperFrames exists as described:
  [heygen-com/hyperframes](https://github.com/heygen-com/hyperframes), Apache-2.0 (compatible with
  later resale), Node >= 22, headless Chrome/Puppeteer + FFmpeg — fits an Actions runner. Still pin
  the version and smoke-test render time per video; community signals show some users moving to
  Remotion, so track upstream activity before phase 2b starts.
- **N9 — WinnerPicker needs entry photo bytes in the Worker.** The port exists
  (`packages/core/src/ports/services.ts`) but the only `MediaSource` (Telegram `getFile`) lives in
  the publisher (`apps/publisher/src/photos/telegram-media-source.ts`). The close/winner task needs a
  small Worker-side getFile client — put it in the task split.
- **N10 — Dead seam in the channel port.** `ChannelAdapter.openPoll` and `PollSpec.photoIndexes`
  (`packages/core/src/ports/channel.ts`) have no implementation and no caller (poll ops go through
  the normal op loop). Remove them now; re-add when a real implementation needs them.

## Answers to the brief's questions

1. **Fit with the code.** Three real contradictions, detailed above: B1 (Worker cannot find message
   ids; ledger/index/callback carry none), B3 (no draft kind in D1, `PublishJob` or the dispatch;
   announcements already publish as `free`; no works build path in `build-post.ts`/`git-repo.ts`),
   and B2 (names in the payload conflicts with ADR 010 itself). Everything else maps cleanly onto
   what exists: the T21 payload/poll schema, `renderTelegram` album+poll ops, `closePoll` in the
   Telegram adapter (plain fetch, Worker-safe), the T20 cron idempotency pattern
   (`deterministicUlid` + `createIfAbsent`), and the callback HMAC scheme.
2. **Placeholders.** Sound — keep them. It is the only option that satisfies all three constraints at
   once: names out of Git, per-channel naming (Telegram shows, Instagram never), clean withdrawal
   without history rewrite. Two adjustments: resolution data comes from the HMAC endpoint, not the
   payload (B2), and one shared resolver in `core` (`resolveEntryNames(text, names, policy)`) used by
   publisher and site so they cannot drift. Semantics: a placeholder whose entry has no name (never
   given, withdrawn, expired) resolves to "Work No N"; a malformed `{entry:...}` token fails the
   render. No simpler alternative survives the constraints.
3. **Draft types.** Split them. `entry` belongs in its own `contest_entries` table with a minimal
   lifecycle (submitted → approved → withdrawn/expired): entries are never translated, previewed or
   published individually, so the draft FSM (`packages/core/src/draft.ts`) does not fit, and the
   per-chat collecting index would fight the author's post draft. `work` belongs on the `drafts`
   table as a new `kind`: it follows exactly the collect → translate → preview → publish cycle the
   FSM already models, with kind extras (collection) alongside. One FSM for publishable things,
   separate small tables for auxiliaries.
4. **Publish workflow.** No risk to idempotency or the ADR 003 exception as long as `site` and
   `render-video` commit nothing (Pages deploy and R2 upload are external; R2 overwrite by content
   key is naturally idempotent). The content/-only bot-identity commit rule stays untouched. Real
   workflow-level risks are the wiring details in N4 (payload-required manual dispatch, stale
   checkout SHA, concurrency groups). All workflow file changes are sensitive PRs needing
   Volodymyr's OK (AGENTS.md) — the ADRs already say so; keep that.
5. **T22.** Survives: the cron scaffolding (window math, deterministic per-week draft id,
   insert-or-ignore, feature flag, fewer-than-2 → tell the author, preview → Publish), plus all of
   T21 (payload schema, render ops, closePoll). Superseded: the candidate rule (entries from
   `contest_entries` via `AuthorEntrySource`, numbered in submission order, not the `published_posts`
   index), and the draft must now carry kind + poll + entry refs with placeholder captions (B3, B2).
   Split below.
6. **Over-engineering check.** Keep the 11.1 table as a roadmap, but write no port files without a
   first implementation. Needed in 1b: `SubmissionSource`/`AuthorEntrySource`, `WinnerPicker`,
   `editMessage` capability. Needed in phase 2: `TextGenerator`, the names endpoint. Defer: `video`
   capability, `MediaStore`, `VideoRenderer` (2b, ADR 012 is already "proposed"), `metrics`
   capability and `EmailList` (phase 3), `ShopProvider` and the `sale` schema (phase 4 — ADR 014
   already says no code before then; apply the same rule to the schema field). Remove the unused
   `openPoll`/`PollSpec.photoIndexes` seam now (N10).
7. **Risks.** Beyond B1-B3: personal data (names, Impressum) leaking into public Actions logs (N5);
   the names endpoint's GET auth scheme is undefined (N6); 90-day anonymization of the winners
   showcase (N3); D1 now stores personal data, so Cloudflare joins the processor list in the
   Datenschutzerklärung (arch section 5 already flags DPAs — keep it on the phase-2 checklist);
   Instagram insights permissions for F25 metrics need verification against the Creator account setup
   during the metrics task; HyperFrames verified (N8), pin and smoke-test before 2b; R2 public URLs
   are unlisted-but-public — acceptable for published videos, state it in the ADR. Nothing in ADR
   011-014 looks unsafe on secrets handling given N5/N6 are applied.

## Proposed task split

Phase 1b remainder (each under ~400 non-test lines; T29 precedes T30/T31, T27 precedes T28):

- **T25 Contest entries (F19 part 2a, `bot`, `core`):** `contest_entries` migration; `/entry` flow
  (one photo, optional name ≤ 30 chars, mandatory consent button); `AuthorEntrySource` implementing
  `SubmissionSource`.
- **T26 Draft kinds (`bot`, `core`):** `drafts.kind` + extras migration; `PublishJob` and dispatch
  carry `type`/`poll`; existing flows keep working; announcements dispatch their real type.
- **T27 Names endpoint and placeholder resolution (`bot`, `publisher`, `core`):**
  `GET /internal/contest-names` (HMAC with timestamp, N6), shared `resolveEntryNames` in core,
  publisher resolves per channel (Telegram names, Instagram anonymous), dry-run fixture, log masking
  (N5).
- **T28 Poll draft cron (F19 part 2b, `bot`):** Monday-open cron builds the `wotw-poll` draft from
  `AuthorEntrySource` (1..N in submission order, `< 2` → tell the author), usual preview and Publish.
- **T29 Callback v2 (`publisher`, `bot`, `core`):** callback body carries per-channel album/poll
  message ids (found by op kind in the publisher); D1 stores them (B1).
- **T30 Close and winner (F19 part 3, `bot`, `ai`):** closing cron stops the poll via the D1 poll id;
  vote rules incl. tie/zero-votes; `WinnerPicker` with entry photos (Worker-side `getFile` client,
  N9); `wotw-result` draft.
- **T31 Withdrawal (`bot`, `channels`):** delete name in D1 → `editMessage` (caption or text, N1) on
  Telegram → anonymous everywhere; site rebuild hook becomes real in phase 2.
- **T32 Instagram adapter (former T24):** scope as in tasks v2, plus anonymous placeholder resolution
  from T27; sensitive (new secrets), needs Volodymyr's OK.

Phase 2 (website; sizing to be confirmed when detailed):

- **T33 Site scaffold (`site`):** Astro static in `apps/site`, `/uk/` + `/de/`, theme from tenant
  config, blog built from the `ContentStore`; manual Pages deploy.
- **T34 Works and collections (`bot`, `publisher`, `core`, `ai`):** `work` draft kind,
  `TextGenerator` descriptions UA/DE, publisher works path (`content/works/<id>/`,
  `content/collections/<slug>.md`), optional channel announcement of a new work.
- **T35 Site pages (`site`):** about, collections/works, contest winners (names via the endpoint),
  legal pages injected from secrets; site stays dark until Volodymyr confirms the legal texts
  (spec Q2).
- **T36 Site job (`workflows`, sensitive):** `site` job after publish with `ref: main` checkout and
  masking (N4/N5); go-live checklist incl. Datenschutzerklärung processor list.
